addendum > spec > build prompt; code style, paths, commands, i18n, UI primitives = this repo.

## 4. Document assumptions that do not fit, and the smallest adaptation

### 4.1 Branch
Docs: create `feat/signature-triage`, merge into main when done. **User request: work directly on `main`.** All
commits go on `main`; no branch is created; nothing is pushed. The "how to merge" item of Done #5 becomes "already
on main".

### 4.2 No Prisma, no Phase 1B importer / lab engine, no lab tables
Docs: extend `prisma/schema.prisma` and the Phase 1B importer; "persist QC changes (`qcLog`)"; "seed stays
idempotent". **Adaptation:** no schema change at all (integration rule: run from CSV/JSON when possible). The engine
parses the six CSVs read-only and applies QC-1/QC-2 in code on every load (deterministic, memoised per process);
`qcLog` is returned by the loader and shown in the UI, so "persisting" it is unnecessary. Seed is untouched. If a
later task ever needs storage, it must be an additive new table in `SCHEMA_SQL` for both SQLite and Postgres, run
with `pnpm test:pg`.

### 4.3 Crew: app crew vs reference crew (decision)
The feature computes on **C001..C004 only** (the real Inspiration4 data; `scale` always on these four). For the
check-in pipeline (T5 draw advisor, T6 "offer the triage summary") there is ONE explicit, labelled link in
`config.ts`:

| App crew | Linked reference panels |
|---|---|
| `bat` | C001 |
| `saraa` | C002 |
| `alex` | C003 |
| `mira` | C004 |

(seed order). Wherever a linked panel is shown or spoken it is labelled as the Inspiration4 reference crew member
("Blood panels: Inspiration4 C001, NASA OSDR data, shown for demonstration"); app names are never presented as the
people who gave the blood. `/signature` and `/demo/signature` use C001..C004 directly (crew switch C001..C004); the
demo script (addendum §5) uses C001, C002, C003.

### 4.4 Route: "Signature tab on the crew dashboard"
The dashboard is a single-screen layout whose `NAV_ITEMS` tabs select panels of one view, and its tab ids are
pinned by an existing test. Adding a tab would restyle it. **Adaptation:** a separate page `/signature` (same
`PageFrame` shell, 2 x 2 cards, stacked on mobile) plus one link button in the dashboard top bar; offline demo at
`/demo/signature`.

### 4.5 Where the CSVs live and how they reach Vercel
Files: `data/nasa/` (5 CSVs, see notes Step 0; the urine file OSD-656 is absent and unused by the engine).
Docs assume `data/` is in the repo; here `.gitignore` ignored `/data/` entirely, so Vercel and CI would never see
them. **Adaptation:** (1) `.gitignore` re-includes `data/nasa/` (done in T-1); (2) the server reads them with
`fs` from `path.join(process.cwd(), "data", "nasa")` (found by name fragment, as spec §3); (3) T1 adds
`outputFileTracingIncludes` in `next.config.ts` for the routes that read them (`/signature`, `/demo/signature`,
`/api/signature/**`, `/api/checkins/**`) with `./data/nasa/**/*.csv`, per
`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/output.md`; T1 verifies after
`pnpm build` that the `.nft.json` traces list the CSVs. Fallback if tracing proves unreliable: a build-time JSON
of the parsed matrix generated by a script from the CSVs (recorded in the notes if used). Client components never
read files; they get computed results as props from server components or the API.

### 4.6 KPI field names for the Daily Strain Score (T5)
Docs: `sleep_hours, sleep_quality, resting_hr, fatigue, mood`. App KPIs (`KPI_KEYS`): `sleep_hours` (h),
`heart_rate` (bpm, asked at the check-in), `mood` (1-5), plus `workload` (1-5); there is **no** sleep-quality and
no fatigue field. **Adaptation:** `sleep_hours -> sleep_hours`, `resting_hr -> heart_rate`, `mood -> mood`;
`sleep_quality` and `fatigue` are left missing for app crew (the reference `daily_strain` already skips a KPI with no
data); `workload` is NOT mapped to fatigue (different question). `dailyStrain` itself keeps the five-key interface
so the fixture test vector (DSS 0.0 / 90.0) and the simulated demo check-ins use all five.

### 4.7 i18n area
`tests/i18n.test.ts` pins exactly five areas (`checkin, crew, dashboard, earth, shell`) and requires every key of an
area to start with `<area>.`. **Adaptation:** `src/i18n/strings/signature.ts` holds keys `dashboard.signature.*`
and `dictionary.ts` merges them into the `dashboard` area; no sixth area. EN and MN key sets identical.

### 4.8 Cosmo tools and system prompt
Docs: register `get_signature_triage`, `get_draw_advice`, `get_space_measurability` as Cosmo tools and add two
sentences to the system prompt. Here `TOOL_DEFINITIONS` is a frozen, byte-stable list whose six names are pinned by
`tests/agent.tools.test.ts`, and the cached prefix (tools + `SYSTEM_PROMPT`) must not change per state.
**Adaptation:** the three tools are defined and executed in `src/server/agent/signature.ts` (`SIGNATURE_TOOL_*`,
same `ToolResult` shape); code picks the tool from the question (deterministic intent detection, like
`questions.ts`), runs it, and passes the result as `facts` in a one-shot directive (the `answerAboutResults`
pattern). The two prompt sentences ride in that directive, after the frozen prompt (the companion-mode convention).
`assertNumbersGrounded` + disclaimer check + `assertNoOrbitClaim` + the existing `FORBIDDEN_REPLY` /
`namesConditionOrDrug` backstops gate every answer; on any failure the template is sent. Scripted mode and missing
API key: always the template.

### 4.9 Mission clock
Docs: "mission clock R+1 / R+45 per beat". The app clock (`MISSION_START_DATE`, `missionDayAt`) counts in-flight days
from launch; the signature panels are days relative to landing (`R+1` = day 1). **Adaptation:** the signature view
uses the selected panel's timepoint as its clock (shown as "day N after landing"), set by the timepoint selector or
by the demo beat; `MISSION_START_DATE`, `clock.ts` and the dashboard are not changed. Re-test "mission day 16 / 22"
is panel day + offset in that landing-relative clock.

### 4.10 Draw-advisor state without a database
Docs: kit counters, re-test dates and "importing an UNEXPECTED panel sets a re-test 3 days later" imply stored
state. **Adaptation:** `drawAdvice(state)` is a pure function; the state (panels up to the current timepoint, kits
= `KITS_TOTAL` minus panels, kits saved, pending re-test) is derived deterministically from the panel list and the
check-in history (or `src/data/demo_checkins.json` in the demo).

### 4.11 Demo audio and commands
Docs: `pnpm demo:audio`, `public/demo/audio/<beat>_<lang>.mp3`, `pnpm lint/test`. The repo's demo audio is keyed
`<lang>-<sha1>.mp3` for check-in turns. **Adaptation:** signature beats use the documented
`public/demo/audio/signature/<beat>_<lang>.mp3` (own sub-folder so the two schemes never collide), generated by the
new `demo:audio` script through the existing TTS helper; missing file = captions only. Commands as in section 1.
`sig:ref` is optional (`python3` 3.11 and `python` 3.13 both exist on this machine); no test depends on Python.

### 4.12 Wording guard scope
Build rule 6 forbids "normal"/"abnormal" as a verdict. Existing app strings use "Normal" as a status word
(`STATUS_WORD`, pinned by `tests/i18n.test.ts`). **Adaptation:** the forbidden-wording test greps only the
signature templates, `dashboard.signature.*` keys and `src/components/signature/*`; existing strings are not changed.
Spec template sentences contain "normal fluids" / "хэвийн ууж" (not a verdict) and are copied verbatim; the guard
test allow-lists exactly that phrase.

### 4.13 Data file names
`MANIFEST.sha256` names `OSD-569_CBC.csv`; the OSDR download is
`OSD-569_LSDS-7_Complete_Blood_Count_CBC_TRANSFORMED.csv` with the same SHA-256. Files are found by name fragment
(`CBC`, `Metabolic_Panel`, `serum_immune`, `cardiovascular`, `Alamar`), so the name difference needs no code. The
addendum's file name `LSDS-8_Multiplex_serum.immune.AlamarPanel_TRANSFORMED.csv` differs from the bundled
`OSD-575_LSDS-8_Alamar_NULISA_serum_TRANSFORMED.csv`; the `Alamar` fragment matches the bundled one.
The CSVs as downloaded have a UTF-8 BOM and **CRLF** line endings (the checksums are over those bytes), so the
parser strips the BOM and splits on `\r?\n`; `.gitattributes` keeps the bytes unchanged in git.
